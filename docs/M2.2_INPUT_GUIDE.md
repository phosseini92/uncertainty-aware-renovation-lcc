# M2.2 input and scope guide

Production BoQ, environmental factor/assignment and transport CSVs are header-only
until documented data are supplied. The
synthetic example is exclusively a verification fixture; do not present its
masses, distances, factors or impacts as real building data.

## Run

```bash
python -m unittest discover -s tests -v
python renovation_lcc.py --horizon-mode legacy_30
python scripts/audit_m2_2.py --baseline /path/to/unmodified/M2.1 --output-root /tmp/m22-audit
```

Additional CLI options:

- `--transport-scenarios inputs/transport_scenarios.csv`
- `--transport-factors inputs/transport_factors.csv`
- `--boq-transport-assignments inputs/boq_transport_assignments.csv`

The existing `--component-boq`, `--environmental-factors` and
`--boq-factor-assignments` options keep their meaning.

## Transport scenarios

`transport_scenario_id` is a stable route identity. Each route records
`origin_scope`, `destination_scope=PROJECT_SITE`, `distance_km`, `transport_mode`,
`vehicle_class`, `load_factor_basis`, `source_status`, `source_reference`,
`retrieval_date` (ISO YYYY-MM-DD), and optional `notes`.

Allowed source statuses: `DOCUMENTED_PROJECT_DATA`, `PUBLIC_DOCUMENTED_DATA`,
`TEST_ONLY_SYNTHETIC`. An empty distance blocks the assignment. Negative,
nonfinite, or malformed supplied distance raises a validation error. Explicitly
documented zero distance is allowed and distinguished from missing evidence.

This version supports one active, single-leg route and the entire documented
mass per BoQ line. It does not support split shipments, multiple legs, extra
packaging/waste mass, a loaded-versus-empty trip model or distance uncertainty.
Do not collapse a mixed-mode route into a made-up average factor. Those cases
need an explicit later schema extension.

## Transport factors

`transport_factors.csv` is independent from the product-factor registry. It uses
the environmental registry columns plus `transport_mode`, `vehicle_class`,
`load_factor_basis`, `factor_system_boundary`, and `retrieval_date`.

Executable records require `indicator_id=GWP_TOTAL`, `module_scope=A4`,
`indicator_unit=kgco2e` and `declared_unit=tkm`. Supported tonne-km spelling
aliases are normalized by the existing registry. Values are per **one** declared
unit: a source expressed per 1,000 tonne-km must first be explicitly normalized
and its derivation cited. Negative/credit transport factors are outside scope.
No summation of GWP_FOSSIL/BIOGENIC/LULUC is permitted.

Source citation, dataset/process identity, verification, data quality, licensing
and uncertainty metadata use the existing registry's validation. The factor's
load/return basis is part of the sourced intensity and is not applied twice.
Mode, vehicle and load-basis strings must match the route. System-boundary text
must state what the sourced transport intensity includes; this checkpoint does
not make datasets with different boundaries equivalent.

The deterministic central factor is used; uncertainty metadata are retained
without sampling. No carbon discounting is applied.

## Assignments and identities

`boq_transport_assignments.csv` links `boq_line_id` to `transport_scenario_id` and
`factor_set_id`, with explicit `scenario_id`, `assignment_id`, `transport_flow_id`,
`active`, `initial_transport_basis`, `mapping_basis`, `mapping_reference`, `notes`.

Only `ASSESSMENT_INVENTORY` BoQ lines are eligible. Exactly zero or one assignment
may be active per BoQ line. Inactive alternatives remain resolved metadata.
`transport_flow_id` denotes one material/BoQ consignment, not a shared truck; it
cannot be active twice in the same building scenario. Product and transport
factor record/set IDs and assignment IDs must be disjoint, keeping ledger joins
unambiguous. Labels and notes do not determine consequence identity.

Allowed mapping bases: `DOCUMENTED_TRANSPORT_PROCESS`, `DOCUMENTED_PROXY`,
`TEST_ONLY_SYNTHETIC`. Every mapping requires a reference; any synthetic input
requires synthetic mapping. These fields retain source claims, not external
verification of their truth.

`NEW_INSTALLATION` applies only to `NEW_AT_T0`. A retained component needs
`DOCUMENTED_RETAINED_T0_TRANSPORT` and a mapping reference documenting actual
initial movement. Without such a declaration no historical A4 is inferred.
Neither path reads replacement events or models replacement transport.

## Mass and activity

The frozen BoQ unit gate is reused to resolve kilograms. A kg or tonne quantity
is sufficient with its documented BoQ source; other units require total
`mass_kg`. An inconsistent quantity and mass field is a hard error.

`tonne-km = resolved_mass_kg / 1000 * distance_km`

`GWP_A4 = tonne-km * kgCO2e_per_tonne_km`

A factor/mass/distance gate can block one line while other lines execute. The
result is explicitly a partial assessed scope, not a whole-building total.
Unknown references and duplicate assignments are structural hard errors.

## Output contract

- `carbon_consequence_ledger.csv`: original product rows, then new A4 rows using
  the same column schema. A4 has `INITIAL_TRANSPORT_TO_SITE`, `reported_module=A4`,
  t=0, generation=0, and no replacement lifecycle event ID.
- `a4_transport_compatibility.csv`: per-active-assignment mass, route, factor,
  tonne-km, source references/dates and gate decision. Join by `assignment_id`.
- `a4_transport_coverage.csv`: every current assessment BoQ line in scope,
  including missing assignments and retained not-applicable cases.
- `assessed_a4_transport_carbon_by_module.csv`: A4 per future/scenario. Futures
  are alternative simulations and must not be summed as one project's carbon.
- `a4_transport_engine_status.json`: A4 scope/counts and missing-data claim guard.
- Three `resolved_transport_*` / `resolved_boq_transport_assignments.csv` files:
  complete normalized scenario/factor/assignment inputs.

For compatibility, `carbon_engine_status.json`, `product_carbon_coverage.csv`
and `assessed_product_carbon_by_module.csv` remain **product-subengine-only**;
their A4 exclusion is relative to that subengine. `run_manifest.json` lists the
combined implemented modules, total/product/A4 counts and input/source hashes.
The frozen `carbon_consequences.validate_carbon_consequence_ledger` validates
only product rows. Use the A4 validator and `append_a4_to_product_ledger` for the
combined path.

Permitted descriptions are module-level results or “assessed product and A4
transport carbon.” Neither a Whole-Life Carbon total nor a whole-building
coverage percentage is supported.

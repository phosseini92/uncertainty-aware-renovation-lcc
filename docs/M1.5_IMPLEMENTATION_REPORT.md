# M1.5 implementation report — retained remaining life vs replacement full service life

Date: 2026-09-27

## Objective

M1.5 introduces an explicit distinction between the **remaining service life of a retained existing component at `t=0`** and the **full service life of a newly installed or replacement generation**. The change is implemented without changing the supplied legacy-compatible component inventory or any default economic result.

The core rule is:

- `NEW_AT_T0`: the first and all later replacement intervals use full service life;
- `RETAINED_EXISTING`: the first replacement interval uses an explicitly declared remaining-life model; every later installed generation uses full service life.

No remaining life is inferred from component age. `age_at_t0_years` is provenance metadata only.

## Implementation

### `component_lifecycle.py`

M1.5 adds optional, backward-compatible lifecycle fields:

- `initial_component_state` (`NEW_AT_T0` or `RETAINED_EXISTING`);
- `age_at_t0_years` (metadata only);
- `remaining_life_distribution`;
- `remaining_life_min_years`;
- `remaining_life_mode_years`;
- `remaining_life_max_years`;
- `remaining_life_fixed_years`;
- `remaining_life_uncertainty_key`;
- `full_life_distribution`;
- `full_life_min_years`;
- `full_life_mode_years`;
- `full_life_max_years`;
- `full_life_fixed_years`;
- `full_life_uncertainty_key`.

The explicit M1.5 fields are optional for legacy-compatible files. If `initial_component_state` is absent, the row is interpreted as `NEW_AT_T0`, and the original v2.1 `lifetime_distribution` / min / mode / max / `uncertainty_key` remain the effective full-life model. This preserves the existing random streams exactly.

For a retained component, the remaining-life model is mandatory. There is no silent fallback to full service life. Missing data raise:

`MISSING_REMAINING_LIFE_MODEL_FOR_RETAINED_COMPONENT`

The engine also rejects remaining-life fields on `NEW_AT_T0` rows so that an ambiguous state cannot be silently accepted.

### Random-stream semantics

The first retained interval uses a dedicated key:

`remaining_life:<remaining_life_uncertainty_key>:initial`

Full-life generations use:

`lifetime:<effective_full_life_uncertainty_key>:renewal:<generation>`

For the supplied default components, the effective full-life key is still the legacy `uncertainty_key`; therefore every pre-M1.5 random draw remains unchanged.

Comparison-lineage validation now requires one component type and one effective **full-life** uncertainty stream per lineage. Retained rows within the same lineage must also share a remaining-life uncertainty key. Remaining-life and full-life keys are intentionally separate.

### `lifecycle_events.py`

Canonical B4 events now record the source of the preceding service-life interval through the existing field `service_life_basis`:

- `REMAINING_LIFE` — allowed only for replacement generation 1;
- `FULL_SERVICE_LIFE` — used for all `NEW_AT_T0` renewals and every later replacement generation.

`random_stream_key` is now passed explicitly by the lifecycle engine so the ledger records the actual stream used. Event identity itself remains based on future/scenario/component/event-type/generation and therefore remains stable when an assumption changes event timing.

## Golden retained-component test

A synthetic test-only retained window uses:

- remaining life: fixed 7 years;
- replacement full life: fixed 20 years.

Expected replacement events are reproduced exactly:

- 30-year RSP: years `7, 27`;
- 50-year RSP: years `7, 27, 47`;
- 60-year RSP: years `7, 27, 47`.

The event at year 67 is outside both the 50- and 60-year RSPs. The first event is labelled `REMAINING_LIFE`; later events are labelled `FULL_SERVICE_LIFE`.

## Data-integrity decisions

The production `inputs/components.csv` is intentionally not edited in M1.5. Its absence of `initial_component_state` invokes the documented legacy compatibility rule `NEW_AT_T0`. A schema-only template is provided at `v3_schema_templates/components_m1_5.csv` for future explicit retained-component inputs.

No building component in the research demonstrator is reclassified as retained until a documented physical reference inventory and remaining-life assumptions are supplied. No remaining-life distribution is invented.

## Scope boundary

M1.5 does **not** add:

- a physical reference inventory;
- conditional survival/reliability modelling from component age;
- residual value at the RSP boundary;
- calendar-year mapping;
- physical quantity/BoQ data;
- carbon factors or carbon consequences;
- B2/B3/B5 event generation.

The next lifecycle step can build the physical reference and/or RSP boundary state on top of the now-separated remaining/full-life semantics without revisiting the legacy full-life streams.

## Gate result

**M1.5 PASS.** Retained-component remaining life and replacement full service life are now distinct, auditable lifecycle concepts while the supplied legacy-compatible 30/50/60-year calculations remain exactly unchanged.

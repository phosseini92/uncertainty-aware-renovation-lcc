# M1.7 Implementation Report — Physical Quantity / BoQ Mapping + Reference Coverage Skeleton

**Checkpoint:** v3-M1.7  
**Date:** 2026-09-27  
**Baseline:** frozen M1.6 reference/boundary implementation  
**Purpose:** add source-backed physical quantity mapping before carbon-factor integration while preserving verified lifecycle and economic behavior.

## 1. Why this milestone exists

The verified v2.1/M1.6 model contains component costs and service-life logic but does not contain a documented bill of quantities for the renovation options. The physical reference interface contains a primary component quantity field when documented rows are supplied, but the production reference inventory is intentionally empty because the source package does not establish existing-building component presence, quantities, ages, or remaining lives.

Carbon consequences therefore cannot be calculated responsibly by interpreting cost as physical quantity or by assigning arbitrary quantities to component labels. M1.7 creates the physical-quantity contract and coverage evidence needed before any environmental factor is introduced.

## 2. Core design decision: component event != one material quantity

A lifecycle component such as a window, heat pump, façade finish, or PV system may map to multiple product/material inventory lines. Forcing a single `event_quantity` and `event_unit` into the canonical event ledger would be ambiguous and would make later double counting more likely.

M1.7 therefore keeps the canonical lifecycle event/state ledgers unchanged and adds a one-to-many bridge:

`component_instance_id -> one or more BoQ lines -> event/state quantity bridge`

The authoritative physical quantity mapping is `inputs/component_boq.csv`. Derived bridge outputs are:

- `lifecycle_event_boq_quantities.csv`
- `rsp_boundary_boq_state.csv`
- `reference_lifecycle_event_boq_quantities.csv`
- `reference_rsp_boundary_boq_state.csv`

The legacy scalar `event_quantity` / `event_unit` fields remain nullable and are not interpreted as zero.

## 3. BoQ contract

Each BoQ row carries:

- stable `boq_line_id`;
- exact scenario/component/lineage/type parent identity;
- item label and stable material/product ID;
- `assessment_role` (`ASSESSMENT_INVENTORY` or `INFORMATION_ONLY`);
- strictly positive physical quantity and explicit unit;
- optional positive `mass_kg`;
- provenance status and source reference;
- derivation method when the quantity is derived from documented geometry.

Supported canonical unit tokens at this checkpoint are `kg`, `t`, `m`, `m2`, `m3`, `unit`, and `kwp`. Lexical forms such as `m²`, `m³`, and `kWp` are normalized, but M1.7 performs **no physical unit conversion**.

No BoQ row is accepted if its stable identity disagrees with its lifecycle-component parent.

## 4. Production evidence state

The production `inputs/component_boq.csv` is intentionally header-only. The source package does not contain documented intervention quantities, so none are fabricated.

Consequently:

- all 13 intervention component instances are reported as `BOQ_MISSING` in `physical_quantity_coverage.csv`;
- lifecycle-event and RSP-state BoQ bridge outputs are header-only in the production run;
- positive `initial_cost_eur` values do not change that status and are never used as quantity proxies.

## 5. Reference presence and coverage skeleton

M1.6 correctly refused to infer reference components from renovation options. M1.7 makes that evidence state machine-readable through `inputs/reference_component_presence.csv`.

For every known intervention lineage the reference declaration must be exactly one of:

- `PRESENT_DOCUMENTED`
- `ABSENT_DOCUMENTED`
- `UNKNOWN`

The supplied production file covers all six known intervention lineages and marks all six `UNKNOWN`, with evidence status `SOURCE_NOT_AVAILABLE_IN_V2_1`.

Important distinctions are enforced:

- documented absence is not the same as missing evidence;
- `PRESENT_DOCUMENTED` requires an executable reference inventory row;
- `ABSENT_DOCUMENTED` forbids an executable row for that lineage;
- `UNKNOWN` cannot coexist with an executable reference inventory row.

`reference_coverage_skeleton.csv` combines presence evidence, physical-reference inventory state, and BoQ availability. Its denominator is explicitly `KNOWN_INTERVENTION_LINEAGES_ONLY`. It is **not** a whole-building coverage percentage and must not be described as one.

Current production output: all six lineages are `REFERENCE_PRESENCE_UNRESOLVED`.

## 6. Double-counting guard introduced before carbon

BoQ rows distinguish:

- `ASSESSMENT_INVENTORY`: intended for future environmental-factor mapping;
- `INFORMATION_ONLY`: physical metadata that must not automatically be added to assessment inventory.

This lets a component retain a useful high-level quantity without silently summing it together with material/product sublines later.

## 7. Lifecycle and economic non-interference

M1.7 joins quantity information to stable component/event identities after lifecycle timing has been generated. It does not change:

- service-life draws;
- random-stream keys;
- replacement timing;
- event IDs;
- boundary-state logic;
- replacement costs;
- scenario NPV/accounting;
- stress, sensitivity, robustness, or convergence equations.

No carbon factor or GWP arithmetic is present in M1.7.

## 9. Scientific claim boundary

M1.7 does **not** provide a building BoQ, environmental LCA, whole-life carbon result, or reference-completeness claim. It provides an auditable architecture that refuses to calculate those quantities until documented physical inputs exist.

The correct current interpretation is:

> The model has a validated lifecycle-linked physical quantity / BoQ interface and explicit reference evidence-coverage skeleton, but the supplied demonstrator lacks source-backed intervention BoQ and reference-side presence evidence.

## 10. Next technical milestone

The next step should be **M1.8 — Environmental Factor Registry + Unit/Declared-Unit Compatibility Gate**, still without producing headline carbon results. It should ingest traceable factor metadata (initially compatible with public/re-distributable sources), validate declared units against BoQ units through an explicit conversion registry, and refuse factor use when provenance, module scope, indicator, or unit compatibility is unresolved.

Only after that registry and compatibility gate pass should the first Carbon Consequence Engine be enabled.

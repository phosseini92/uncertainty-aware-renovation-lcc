# M1.6 Implementation Report — Physical Reference Inventory Gate + RSP Boundary State

Date: 2026-09-27  
Checkpoint: `v3-M1.6`

## 1. Scope

M1.6 implements two lifecycle prerequisites without changing the verified v2.1 incremental economics:

1. an RSP-boundary component-state ledger for 30/50/60-year analyses; and
2. an executable physical-reference inventory schema/gate for the Minimum-Intervention Continued-Use Reference.

No carbon factors, residual-value credit, end-of-life assumptions or absolute-reference cash flows are added.

## 2. Design refinement discovered during implementation

The earlier design listed `RSP_BOUNDARY_STATE` among lifecycle event types. M1.6 corrects this semantic issue: reaching the reference-study-period boundary is an **accounting observation point**, not necessarily a physical event. Boundary observations therefore live in `rsp_boundary_state.csv`, separate from `lifecycle_event_ledger.csv`. The physical event ledger remains restricted to actual lifecycle events.

## 3. RSP boundary-state model

For each future/component stream, the shared lifecycle engine now records exactly one state at the RSP. The state includes:

- installed component generation at the boundary;
- initial component state (`NEW_AT_T0` / `RETAINED_EXISTING`);
- assessment interval start;
- installation time where physically knowable;
- age within the assessment interval;
- physical age at the boundary where source-backed;
- next modeled replacement time;
- remaining life at the boundary;
- sampled life of the current interval;
- life basis and random-stream key; and
- whether a replacement is due exactly at the RSP.

The identity is stable on `future_id + scenario_id + component_instance_id + RSP` and is independent of display labels.

The event rule remains strictly `event_time < RSP`. If a replacement is due exactly at the boundary, the event is excluded while the boundary state reports zero remaining life and `replacement_due_at_boundary = true`.

## 4. Retained-component semantics at the boundary

For a retained generation-0 component:

- the current interval is governed by `REMAINING_LIFE`;
- if `age_at_t0_years` is documented, physical installation time is `-age_at_t0_years` and physical age at the RSP is available;
- if age is not documented, installation time and physical age remain missing rather than being invented; and
- `age_within_assessment_years` remains available as the time elapsed since t=0.

After the first replacement, all in-service replacement generations use `FULL_SERVICE_LIFE`.

## 5. Physical reference inventory

The executable schema is implemented in `inputs/physical_reference_inventory.csv` and validated by `reference_inventory.py`.

An executable row requires:

- explicit stable scenario/component/type/lineage IDs;
- the declared reference `scenario_id`;
- positive physical quantity and nonempty unit;
- explicit full-life model;
- explicit remaining-life model for retained components;
- a source-status declaration and source reference; and
- M1.5 age/life-model consistency.

Reference lifecycle scheduling reuses the same physical lifecycle engine as renovation components. Its temporary economic fields are set to zero so physical baseline renewals do **not** redefine the verified zero-cash-flow reference NPV in compatibility mode.

## 6. Why the production reference inventory is empty

The v2.1 source package documents intervention cost allocations and illustrative service lives, but it does **not** provide a source-backed inventory of the existing building's physical components, physical quantities/units, installation ages, or remaining-life evidence. M1.6 therefore does not infer baseline components from renovation options.

The production `inputs/physical_reference_inventory.csv` is intentionally header-only. `reference_inventory_status.json` reports:

`UNPOPULATED_SOURCE_DATA_ABSENT`

`inputs/reference_inventory_gap_register.csv` lists intervention lineages for which reference-side evidence remains unresolved. Those rows are a gap register only and are not treated as evidence that the same component exists in the reference building.

Synthetic reference rows are permitted only in tests and must be marked `TEST_ONLY_SYNTHETIC`.

The suite increased from 47 to **62 tests**, all passing. Python byte-compilation passes.

Each 10,000-future boundary file contains exactly **130,000 rows** (13 intervention component instances × 10,000 futures) and 130,000 unique boundary-state IDs.

## 9. Cross-horizon reconciliation

A stronger audit was performed by comparing each shorter-RSP boundary state's next modeled replacement to the longer-RSP event ledger.

- 30 → 50 years: 106,613 boundary next-replacements fall before year 50; **0 missing**, and every event time matches exactly.
- 50 → 60 years: 47,605 boundary next-replacements fall before year 60; **0 missing**, and every event time matches exactly.

This confirms that the boundary state is a consistent view of the same nested lifecycle streams rather than a separately sampled schedule.

## 10. Performance guard

Boundary-state construction is requested only by the dedicated M1.6 wrapper. Legacy sensitivity/convergence routines do not build unused boundary tables. A full default 10,000-future run with convergence diagnostics and charts completed successfully after this guard was added.

## 12. Next dependency

Residual value should remain disabled until an explicit boundary-value method is specified and tested. The carbon consequence engine may be developed for documented intervention components, but any whole-building/reference comparison must retain an explicit incomplete-reference coverage status until the physical reference inventory is populated with source-backed data.

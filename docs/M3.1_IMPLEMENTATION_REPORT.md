# M3.1 Implementation & Audit Report

## Milestone

**M3.1 — B6 Operational Energy Carbon Consequences**

M3.1 adds a deliberately narrow operational-energy carbon layer to the frozen M2.6 baseline. It does not infer physical energy use from the legacy economic `annual_energy_savings_kwh` proxy and it does not implement Module D.

## Implemented physical-flow model

The production schema records explicit annual energy flows by scenario and carrier using four controlled flow types:

- `IMPORTED` — energy crossing into the assessed building/system and eligible for B6 GWP when an explicit factor schedule is complete;
- `GENERATED` — onsite generation, tracked for physical bookkeeping only;
- `SELF_CONSUMED` — onsite generation consumed within the assessed system, tracked for balance only;
- `EXPORTED` — onsite generation exported beyond the assessed system, tracked explicitly but **not credited or netted in B6 or A–C**.

For each scenario/carrier/year, `SELF_CONSUMED + EXPORTED <= GENERATED` is enforced. Overlapping interval declarations for the same scenario/carrier/flow type are rejected so annual quantities are unambiguous. Curtailment/losses may be documented by allowing generation to exceed self-consumption plus export.

## B6 factor schedule

`inputs/operational_energy_factor_schedule.csv` maps an explicit `analysis_year` to an explicit `calendar_year` and an environmental `factor_set_id`. Executable factors must contain exactly one `GWP_TOTAL` record with exact source scope `B6` and declared unit `kwh`.

The future-factor policy is intentionally conservative:

`EXPLICIT_ANNUAL_SCHEDULE_ERROR_IF_MISSING_NO_INTERPOLATION_NO_EXTRAPOLATION`

A missing in-RSP year blocks the entire affected imported-energy flow rather than silently carrying a factor forward, interpolating, extrapolating, or treating the year as zero. Schedule calendar mapping must use one consistent analysis-year/calendar-year offset.

## Consequence semantics

For each imported flow with complete schedule coverage:

`B6 GWP = annual imported kWh × explicit calendar-mapped GWP_TOTAL factor`

One deterministic consequence row is emitted per future and active analysis year. The row uses `reported_module=B6`, `source_factor_module_scope=B6`, `consequence_type=B6_OPERATIONAL_ENERGY_IMPORT`, and midpoint timing `event_time_years = analysis_year - 0.5` so each annual flow lies within the selected RSP interval.

Environmental-factor uncertainty metadata is carried into the ledger but is not sampled in M3.1. Carbon is not discounted.

## Export boundary

M3.1 does **not** calculate D2. Exported energy remains a physical flow with status `TRACKED_ONLY_D2_DEFERRED_NOT_NETTED_IN_A_C`. No negative B6 import, avoided-grid credit, or export offset is created. This keeps the later Module-D layer separate and prevents premature A–C netting.

## Production-data boundary

`inputs/operational_energy_flows.csv` and `inputs/operational_energy_factor_schedule.csv` are intentionally header-only. The inherited demonstrator does not contain source-backed operational carrier flows or calendar-year carbon factors. The production default therefore reports `NO_OPERATIONAL_ENERGY_FLOWS`, meaning **not assessed**, not zero.

## Validation

Dedicated M3.1 tests cover schema, explicit schedule requirements, nonnegative flows, interval overlap, year-by-year generated/self-consumed/exported balance, exact B6/GWP_TOTAL/kWh factor scope, rejection of negative B6 credits, calendar mapping, missing-year blocking, carrier mismatch, closed-form carbon, RSP truncation, export separation, explicit-zero semantics, factor-uncertainty metadata, default production status, full-run integration, and isolation from the legacy economic savings proxy.

Closed-form fixture:

- year 1: `100 kWh × 0.5 kgCO2e/kWh = 50 kgCO2e`;
- year 2: `100 kWh × 0.4 kgCO2e/kWh = 40 kgCO2e`;
- total B6 = **90 kgCO2e per future**.

Changing `annual_energy_savings_kwh` in the legacy scenario file leaves the B6 consequence rows unchanged when explicit B6 flow/schedule inputs are held fixed.

## Regression and parity

Independent 10,000-future runs with seed `20260726` were executed at `legacy_30`, `levels_50`, and `rics_60`. For each horizon, all **76 common non-manifest M2.6 outputs are byte-identical**. M3.1 adds only the operational flow/schedule resolution, coverage, summary and status outputs when production B6 inputs remain empty.

A full default 10,000-future run with convergence diagnostics and charts completed successfully.

## Scientific boundary after M3.1

Implemented carbon modules now include A1–A3, A4, A5.1/A5.2/A5.3, the complete B4 replacement event family, and B6 operational energy. The framework still does not produce a Whole-Life Carbon headline because terminal C1–C4, separate Module D, applicability/coverage aggregation, and other deferred use-stage modules remain unresolved.

**PASS / freeze-ready for the implemented M3.1 B6 scope.**

# M2.2 — Initial A4 Transport Carbon Consequences

## Delivered scope

Initial A4 transport is an independent consequence layer on the verified M2.1
package. It consumes documented BoQ mass, an explicit route/distance and a
separate transport-process factor registry. It never samples service life,
changes replacement timing, samples transport uncertainty, discounts carbon or
adds replacement transport to B4.

## Implementation

- New `a4_transport.py`: registry/scenario/assignment validation, mass-distance

- `environmental_factors.py`: existing validation body extracted into a callable

  v3-M2.2. No original tests were removed or weakened.

## Scientific and accounting contract

`tonne-km = documented mass_kg / 1000 * documented distance_km`

`GWP_A4 = tonne-km * GWP_TOTAL transport intensity`

A mass-based BoQ or documented total-mass bridge is required. The frozen unit gate
reconciles conflicting kg/tonne quantities and mass fields. No cost-, density-
or geometry-based quantity inference is added.

GWP_TOTAL must be explicit in an A4 transport record expressed per tonne-km.
Disaggregated GWP indicators are not summed. Mode, vehicle and load basis must
match the route. Factor boundary and retrieval date are retained; load and return
assumptions are never reapplied as multipliers. Only the central factor value is
used, with static-factor and no-uncertainty provenance on each consequence.

Each A4 row is `INITIAL_TRANSPORT_TO_SITE`, reported to A4, at t=0, generation 0,
with no replacement event ID. Stable IDs use future, component, BoQ, flow and
factor identities, independent of display labels and horizon. Retained historical
components are excluded unless a documented actual t=0 movement is explicitly
assigned. Replacement transport is not an A4 row in this checkpoint.

One active route is allowed per assessment BoQ line. Duplicate active flows,
unknown identities, informational quantities, and scenario/parent mismatches are
rejected. Missing mass, distance, GWP_TOTAL, or executable factor scope produces a
coverage block. Partial coverage cannot become a whole-building or whole-life
claim. A sourced zero-distance route is distinguished from missing distance.

## Output compatibility

The combined carbon ledger keeps its original columns and appends A4 rows after
unchanged product rows. The three product-only files remain unchanged:
`assessed_product_carbon_by_module.csv`, `product_carbon_coverage.csv`, and
`carbon_engine_status.json`. The latter remains the M2.1 **product subengine**
status, including its A4 exclusion; combined scope is in `run_manifest.json`.

Seven outputs are additive:

1. `resolved_transport_scenarios.csv`
2. `resolved_transport_factors.csv`
3. `resolved_boq_transport_assignments.csv`
4. `a4_transport_compatibility.csv`
5. `a4_transport_coverage.csv`
6. `assessed_a4_transport_carbon_by_module.csv`

Join A4 ledger rows to assignment and compatibility outputs using `assignment_id`.
That bridge retains mass, source references, distance, route, transport-flow ID,
vehicle/load/system-boundary basis, factor record and retrieval dates. Factor and
assignment IDs are disjoint across product/transport registries.

## Verification design

The original package was run first: 109/109 tests passed. M2.2 adds 33 tests,
including the closed form 1000 kg × 100 km × 0.1 kgCO2e/tkm = 10 kgCO2e, mass
bridges, missing data, wrong units/modules, factor-basis mismatch, duplicates,
retained movement semantics, scope isolation and real full-run integration.

The populated integration test uses canonical heat-pump replacement events to
ensure B4 is genuinely present at all three horizons. Doubling only distance
changes A4 from 10 to 20 kgCO2e while product rows, product status/summary,
canonical events and economic outputs remain byte-identical.

Independent subprocess parity runs compare M2.1 and M2.2 with 10,000 futures,
seed 20260726 and 30/50/60-year profiles, without charts/convergence. Both
production-empty and populated synthetic cases are audited. For the synthetic
case, original CSV product records are compared as bytes after removing only
appended A4 records; they are not reserialized before comparison.

### Audit execution note

Preliminary runs in the active workspace produced a truncated legacy replacement
CSV, first observed at 50 years (162,452 rows rather than 209,348). A repeat passed,
but later checks detected post-export changes at 60 years in both baseline and
candidate executions. Those artifacts were rejected, and their cause was not
established. No model or CSV-writer patch was introduced to force parity.

The final run used fresh copies in an isolated temporary directory. The same
read-only harness checked each exported CSV's row count against its in-memory
DataFrame, then checked its hash again after model completion. All 12 parity
runs (two versions x three horizons x two input cases) and the full default run
passed. Every compared file hash was checked again after the entire sequence;
all remained unchanged. The delivered default outputs were copied from this
verified run and checked byte-for-byte. This validates the delivered artifacts;
it does not claim a diagnosed or universally fixed filesystem issue.

The audit reader emitted one pandas mixed-type warning for the optional
lifecycle-event ID column. CSV byte comparisons were unaffected. Its read now
uses `low_memory=False`; all three saved populated ledgers were reread and
checked after this change. Model code, calculations and exports did not change.

## Production readiness limits

The engine is executable; a real project carbon assessment is not populated.
Production status remains `NO_ASSESSMENT_BOQ_LINES`, with an empty ledger. No
mass, distance, factor or reference inventory has been invented. The synthetic
fixture lives only under `tests/fixtures/m22_transport_synthetic/` and is clearly
marked TEST_ONLY_SYNTHETIC.

M2.2 models one full-mass single-leg initial flow per BoQ line. Split/multi-leg
routes, packaging/waste allowances, time-dependent transport intensities,
replacement transport, A5/C/D/B6, residual value, MAC and stakeholder-carbon
allocation remain outside scope. Validation checks internal consistency and
required source declarations, not the external truth of supplied evidence.

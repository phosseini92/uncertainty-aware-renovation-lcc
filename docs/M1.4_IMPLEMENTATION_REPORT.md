# M1.4 implementation report — 30/50/60-year horizon architecture

## Scope

M1.4 separates the reference study period from the historical 30-year default
while preserving exact 30-year v2.1/M1.3 economic and lifecycle outputs. It does
not change cash-flow equations, service-life distributions, random streams,
event identity, component inputs, physical quantities or carbon accounting.

## Implementation

A new `horizon.py` module defines three named profiles:

| profile | years | use |
|---|---:|---|
| `legacy_30` | 30 | exact v2.1 continuity horizon |
| `levels_50` | 50 | primary Level(s)-aligned research horizon |
| `rics_60` | 60 | optional RICS-WLCA-aligned comparison horizon |

`resolve_horizon()` deep-copies the loaded model configuration. With no profile
override it preserves `analysis_years` exactly. With a named profile it changes
only that runtime field. The supplied `inputs/model_config.json` remains
unchanged at 30 years.

`renovation_lcc.py` now accepts `--horizon-mode` and writes
`resolved_horizon.json`, which records the profile, years, whether the value came
from the config or an explicit profile override, the strict event-boundary rule,
and the no-linear-scaling rule.

## Boundary semantics

The pre-existing lifecycle condition remains:

`event_time_years < analysis_years`

Therefore replacement events exactly at the RSP boundary are excluded. This was
verified independently at 30, 50 and 60 years with fixed 10-year service lives.

## Stable event identity across horizons

Horizon length is deliberately absent from canonical `event_id`. For the same
seed, future, scenario, component and generation, a logical event shared by two
horizons is the same event. Longer horizons only add later generations.

In the documented 10,000-future runs (seed `20260726`):

| horizon | events | unique IDs | maximum event time (years) |
|---:|---:|---:|---:|
| 30 | 94,164 | 94,164 | 29.99905558894424 |
| 50 | 209,348 | 209,348 | 49.99953939260688 |
| 60 | 256,953 | 256,953 | 59.99982974381896 |

The 30-year event-ID set is a strict subset of the 50-year set; the 50-year set
is a strict subset of the 60-year set. For all shared events, selected physical
fields are exactly equal: event ID, future/scenario/component/lineage identity,
generation, event type/time, random-stream key, sampled service life and service-
life basis.

## 30-year regression parity

M1.3 and M1.4 were run independently with 10,000 futures and seed `20260726`,
with charts and convergence disabled only to isolate core numerical outputs.
All **19 common CSV outputs** were byte-for-byte identical. In addition,
`resolved_config.json` and `analysis_report.txt` were byte-identical.

The only new default-run metadata file is `resolved_horizon.json`; `run_manifest.json`
also records the M1.4 checkpoint and horizon metadata.

## Scientific boundary

The profile names indicate intended methodological comparison conventions only;
they do not assert formal Level(s), RICS or EN 15978 compliance. A 50- or 60-year
RSP is an accounting horizon, not a forecast of demolition at that year.

M1.4 does not introduce retained-component remaining-life logic. All current
legacy components still begin with the same full-service-life semantics frozen
through M1.3. That distinction is the next migration substep.

## Gate decision

**M1.4 PASS.** The horizon architecture can be frozen before implementing
retained-component remaining life versus replacement full service life.

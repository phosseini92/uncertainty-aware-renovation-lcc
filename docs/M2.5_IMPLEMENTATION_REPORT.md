# M2.5 — A5.1 Pre-Construction Removal Consequences

## Scope

M2.5 implements the audited v3 removal-at-t0 accounting boundary for **A5.1** only. It is additive to M2.4 and does not alter A1-A3, A4, B4 product, B4 transport, A5.2/A5.3, lifecycle timing, economics, random streams, or RSP-boundary state.

For every explicitly documented removed-existing inventory line, A5.1 may contain three independently traceable subconsequences:

1. deconstruction / strip-out / removal activity;
2. outbound transport of the removed pre-existing material from the project site; and
3. waste processing or disposal attributable to that removed pre-existing material.

D1 recovery benefits/loads remain separately deferred. No C-stage event is generated from the same t0 removed quantity.

## Executable architecture

New module: `a5_1_removal.py`.

New production inputs, intentionally header-only until source-backed data exist:

- `inputs/preconstruction_removal_scenarios.csv`
- `inputs/removal_transport_scenarios.csv`
- `inputs/preconstruction_waste_routes.csv`

The removal inventory is structurally separate from the current-construction BoQ. `removal_inventory_line_id` and `removed_component_instance_id` are required to be disjoint from current-construction BoQ/component identities. This is the primary A5.1/A5.3 double-counting guard.

### Factor ownership

- removal activity: source factor must provide `GWP_TOTAL` scoped to `A5.1`;
- removed-material transport: source transport process retains `A4` factor provenance but the consequence reports to `A5.1`;
- removed-material processing/disposal: the source process retains `C3` or `C4` provenance according to the explicit route type but the consequence reports to `A5.1` under the adopted retrofit accounting split.

No source factor is silently re-labelled inside its registry. Both source scope and reporting scope remain visible in `carbon_consequence_ledger.csv`.

## Quantity and route gates

- Removed quantity must be finite, positive and explicitly unit-tagged.
- A documented `removed_mass_kg` bridge is required where outbound transport or mass-based waste factors cannot be resolved directly from the removed quantity unit.
- Missing distance is blocked; documented zero distance is a valid zero activity.
- Transport activity is `removed_mass_kg / 1000 × distance_km` in tonne-km.
- Removal activity quantity is explicit; no activity is inferred from cost, material label, or removed quantity.
- Waste processing/disposal uses only the explicit removed quantity or documented mass bridge.
- No density, geometry, demolition-rate, recovery-rate, disposal split, or cost-to-quantity inference is performed.

## Double-counting boundary

A physical t0 removed-existing inventory line is owned by A5.1. The same removal inventory identity cannot be used as an A5.3 current-construction BoQ line. M2.5 does not generate C1-C4 rows for the t0 removal. A declared `d1_recovery_scenario_id` is retained as metadata only; no D1 credit/load is calculated in this milestone.

## Production-data integrity

The inherited source package contains no documented removed-existing inventory, deconstruction activity, outbound removal route, or waste-treatment route. Production M2.5 input tables therefore remain header-only. The default engine status is `NO_PRECONSTRUCTION_REMOVAL_INVENTORY`, which means **not assessed**, not zero carbon.

Synthetic values exist only in tests.

## Purpose

M3.1.1 is a narrow hardening patch. It changes **no B6 arithmetic equation**, no lifecycle-event generation, no economic equation, and no random stream. Its purpose is to close release/documentation/configuration inconsistencies identified by the M3.1 hard-freeze audit before any C/D implementation begins.

## Closed audit findings

1. **Scientific specification / runtime config mismatch — CLOSED**  
   `inputs/model_config.json` now explicitly declares:
   - `assessment_convention = EN15978_2026_INFORMED`;
   - `generated_energy_reporting_approach = PHYSICAL_FLOWS_B6_IMPORT_ONLY_D2_DEFERRED`;
   - `factor_extrapolation_policy = ERROR_IF_MISSING`.
   The main runner validates these fields and passes the B6 policy fields into the operational engine. Unsupported future-factor or generated-energy policies are rejected rather than silently interpreted.

2. **Broken README evidence links — CLOSED**  
   The source release no longer links to a non-existent committed `outputs/` directory. README now points to versioned audit documents and states that generated outputs/charts are regenerated locally.

3. **Top-level validation summary stale — CLOSED**  
   `VALIDATION.md` now includes M3.1 B6 evidence and M3.1.1 hardening/parity results.

4. **CHANGELOG heading/order corruption — CLOSED**  
   M3.1.1 is added as the active checkpoint and the misplaced M1.8 heading is restored to its own section.

5. **Public version metadata ambiguity — CLOSED**  
   README distinguishes `research checkpoint v3-M3.1.1` from the inherited `economic core v2.1`; `CITATION.cff` is updated to version `3.1.1`, release date 2026-09-28, and current scope language. The run manifest now records `model_version=3.1.1-research`, `economic_core_version=2.1`, and `migration_checkpoint=v3-M3.1.1-HARDENING`.

6. **Historical checksum manifests at repository root — CLOSED**  
   Historical M1.x/M2.x/M3.1 checksum manifests were moved to `provenance/historical_checksums/` with an explanatory README. Root-level checksum manifests describe the current release only.

7. **Calendar-year versus factor `reference_year` ambiguity — CLOSED**  
   The operational schedule `calendar_year` is explicitly defined as the **factor application year**. Environmental-factor `reference_year` is the **dataset/source reference vintage** for provenance and is not required to equal the application year. No future trajectory is inferred from `reference_year`.

## Numerical-behaviour guard

The only Python-source edits relative to M3.1 are policy validation/pass-through and run/status metadata in `renovation_lcc.py` and `b6_operational.py`. B6 consequence construction remains:

`GWP_B6,y = imported_energy_kWh,y × explicit scheduled GWP_TOTAL factor_y`

The M3.1 rules remain unchanged:

- only `IMPORTED` flow creates B6 consequences;
- `GENERATED`, `SELF_CONSUMED`, and `EXPORTED` remain bookkeeping flows;
- export receives no B6 credit and D2 remains deferred;
- no interpolation, extrapolation, carry-forward or assumed decarbonisation;
- missing factor years block the affected imported flow;
- legacy `annual_energy_savings_kwh` is not a physical B6 inventory;
- Whole-Life Carbon/headline carbon remains disabled.
